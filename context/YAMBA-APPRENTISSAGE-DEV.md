

## Chapitre 158 — ADM-SEC · Tester une connexion à deux facteurs sans téléphone, sans rien bloquer, et relire ce qui a été écrit
Quatre enseignements. (1) **Un code TOTP se calcule** : RFC 6238, HMAC-SHA1 du secret sur le numéro du pas de 30 s (`floor(epoch / 30)`), tronqué à six chiffres. Le harnais importe la même bibliothèque que le serveur (`packages/libs/totp`) et calcule `totpCode(secret)` — exactement ce que fait Google Authenticator. Conséquence pour l'anti-rejeu : un code est unique à un pas ; pour prouver qu'un code consommé est refusé, la fiche attend le DÉBUT d'un pas (`30 - epoch % 30`) afin que connexion, déconnexion et rejeu tiennent dans les mêmes trente secondes. (2) **Ce qui consomme ou bloque se joue sur un compte jetable** : six codes de secours, un blocage de quinze minutes, un enrôlement unique — sur un compte partagé, chaque chapitre suivant en paierait le prix. Le compte se crée par le chemin réel (inscription, puis `grant-admin.ts`, dont la sortie est vérifiée) et se détruit dans `afterAll` (`--revoke`, puis suppression) — même en cas d'échec. (3) **Une attente longue se loge dans une autre** : le blocage de quinze minutes démarre, la fiche du délai de cinq minutes se joue sur un autre compte pendant ce temps, puis une fiche « 2/2 » attend l'heure de levée mémorisée. Le chapitre dure 17 minutes au lieu de 20+. (4) **Relire le journal par l'API que lit l'administrateur, borné dans le temps** : un journal jamais purgé contient toutes les exécutions passées, et une borne trop serrée ramasse la fiche d'avant (une seconde de marge a suffi à attraper deux lignes d'une connexion précédente). Et l'anomalie trouvée rappelle une règle déjà vue côté membre : un écran qui traduit un statut HTTP (« 401 → Code invalide ») au lieu du `details.code` que le serveur envoie ment à l'utilisateur au pire moment — quand il tape enfin le bon code.
